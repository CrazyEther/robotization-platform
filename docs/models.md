# Доменные модели и границы доказательности

Версии: `constant-annual-economics/1.0.0`, `process-models/1.0.0`, `observed-replay/1.0.0`, `fcfs-flow/1.0.0`.

Это чистые TypeScript-функции без React, HTTP, базы данных и случайных чисел. Реализация находится в `packages/domain`. Наличие движка не подтверждает наличие реального клиентского набора или успешной демонстрации.

## Контракт входа и результата

Каждое измерение: `{ value: number, unit: string, sourceRef: string }`. `sourceRef` — непустой идентификатор доказательства либо ссылка на исходный документ. Домен проверяет синтаксис ссылки; разрешение ссылки в реестр с checksum, датой, условиями использования и исходным локатором обязан выполнять слой импорта/API. Введённая ссылка сама по себе не подтверждает истинность числа. В частности, паспортный максимум не превращается в эффективную производительность из-за подходящего названия поля.

Функции `evaluateEconomics(raw)`, `evaluateModel(raw)`, `replaySimulation(raw)` и `simulateFlow(raw)` принимают `unknown`, валидируют Zod-схемами и возвращают `{ status, missing, errors, metrics, trace, version }`. Статусы: `complete`, `incomplete`, `invalid`. `complete` означает достаточность и математическую валидность переданных данных для этой версии модели, а не проверенность источников и не промышленную пригодность решения. `null` у KPI означает неопределимость, отсутствие исходных данных либо неприменимость показателя; это не ноль.

Отсутствующее поле не получает значение по умолчанию. Строки не приводятся к числам. Единицы сравниваются строго, коэффициенты и нули должны быть заданы явно. Неизвестные поля запрещены: это позволяет выявлять устаревший mapping. Переполнение даёт `invalid` и `null`, а не `Infinity`. `trace` содержит формулу и ссылки на входы. `economicFields` и `modelFields` публикуют определения полей для UI.

## Экономика

Вход: `currency` (трёхбуквенный код), `vat` (`included`/`excluded`), `mode` (`purchase`/`lease`/`subscription`), `horizonYears` (целое 1–100), `inputs`, `benefits`, `benefitsConfirmed`, `annualAmountsConstant`. Валюта и режим НДС уже должны быть одинаковыми для всех слагаемых; движок не угадывает курс или ставку НДС.

Обязательные агрегаты `inputs`: `capex` в выбранной валюте; `annualOpex`, `annualOtherCosts`, `annualRetainedCosts` в `ВАЛЮТА/year`. Первоначальные затраты включают оборудование, внедрение, инфраструктуру, запуск ПО, обучение и резерв. Аренда/подписка включается в OPEX, первоначальный платёж — в CAPEX. Режим приобретения не обнуляет затраты автоматически. Сохранённые затраты процесса включаются в TCO; они не вычитаются второй раз из приростной выгоды.

Выгода: `{ id, kind, value, unit, sourceRef, overlapKey }`. Денежные `kind`: `cash_saving`, `avoided_hire`, `margin`, `loss_reduction`, единица `ВАЛЮТА/year`. Для одной экономической причины должен использоваться один `overlapKey`: повтор среди денежных выгод блокирует расчёт. `time_released` имеет единицу `h/year`, отражается отдельно и не монетизируется автоматически; `nonfinancial` не входит в денежные KPI. Слой квалификации должен проверять смысл ключей: два разных ключа не доказывают отсутствие пересечения. `benefitsConfirmed: true` явно подтверждает полноту списка, включая пустой список как нулевую суммарную выгоду. Без подтверждения результат неполон.

Версия поддерживает постоянные годовые суммы на горизонте только при `annualAmountsConstant: true`. Не поддерживает скрытое ежегодное повышение зарплаты, инфляцию, остаточную стоимость, оборотный капитал, налог на прибыль или произвольный график платежей.

| KPI / ключ | Формула и единица |
|---|---|
| CAPEX / `CAPEX` | `capex`, валюта |
| Годовой OPEX / `annualOPEX` | `annualOpex`, валюта/год |
| Валовая выгода / `grossBenefit` | сумма непересекающихся денежных выгод, валюта/год |
| Чистый эффект / `netEffect` | выгода − OPEX − прочие дополнительные затраты, валюта/год |
| Окупаемость / `payback` | CAPEX / положительный годовой чистый эффект, годы; иначе `null` |
| ROI горизонта / `roi` | `(эффект × годы − CAPEX) / CAPEX × 100`, проценты; при CAPEX=0 — `null` |
| TCO / `tco` | `CAPEX + годы × (OPEX + дополнительные + сохраняемые затраты)`, валюта |
| Высвобождённое время / `releasedHours` | сумма явно заявленных часов, часы/год; не денежная экономия |
| NPV / `npv` | `−CAPEX + Σ((inflow_t − outflow_t)/(1+discountRate)^t)`, валюта |

NPV появляется только с явной `discountRate > -1` (доля, не проценты) и `cashFlows: [{ year, inflow: Measurement, outflow: Measurement }]`. Потоки — суммы в валюте на конец каждого года; все годы горизонта должны присутствовать по одному разу. Для этой версии они должны согласовываться с постоянной валовой выгодой и OPEX+прочими дополнительными затратами. Движок не генерирует потоки из годовой ставки и не смешивает разные модели ROI и NPV. При заданной ставке и отсутствующих потоках остальные KPI могут быть рассчитаны, но общий результат остаётся `incomplete`. Отсутствие ставки оставляет NPV `null` без блокирования остальных KPI.

## Шесть процессных адаптеров

Вход `evaluateModel`: `{ kind, inputs: Record<string, Measurement> }`. Каждое перечисленное поле обязательно. Число ресурсов положительно и целое, длительности окна положительны. `ratio` лежит в [0,1]; количество и площадь неотрицательны.

| kind | Измерения | Расчёт и ограничение |
|---|---|---|
| `flow` | `requiredThroughput`, `effectiveUnitThroughput`: `operations/h`; `availableHours`: `h`; `availableUnits`: `count` | `ceil(спрос/эффективная производительность)`; доступная мощность и дефицит. Эффективная производительность должна уже учитывать реальные задержки и режим. Нет автоматически добавленного резерва. |
| `coverage` | `cleanableArea`: `m2`; `effectiveAreaRate`: `m2/h`; `availableHours`: `h`; `availableUnits`: `count` | Ресурсы для обработки заданной площади в окне, время, мощность и дефицит площади. Общая площадь здания не подменяет обрабатываемую площадь. Уборка не является доказанной дезинфекцией. |
| `workcell` | `requiredThroughput`: `operations/h`; `cycleSeconds`: `s/operation`; `availability`, `goodYield`: `ratio`; `availableHours`: `h`; `availableUnits`: `count` | Эффективная мощность единицы `3600/cycleSeconds × availability × goodYield`. Не дублировать потери в цикле и коэффициентах. Нулевой выход/доступность означает невозможность определить конечное нужное число ресурсов. |
| `inspection` | `truePositive`, `trueNegative`, `falsePositive`, `falseNegative`: `count`; `observationHours`: `h` | Полнота, точность, специфичность, ошибки, проверенные изделия/час. Требуется независимая проверка истинности; счётчики относятся к одной выборке и периоду. Пустой знаменатель даёт `null`, не идеальное качество. |
| `inventory` | `observedLocations`, `expectedLocations`, `discrepanciesDetected`, `discrepanciesResolved`: `count`; `observationHours`: `h` | Покрытие, доля расхождений и исправлений, остаток, места/час. Проверенные места уникальны, обнаруженные не превышают проверенные, исправленные не превышают обнаруженные. Сканирование не считается исправлением. |
| `digital` | `documentCount`: `count`; `manualSecondsPerDocument`, `automatedSecondsPerDocument`, `exceptionSecondsPerDocument`, `monitoringSecondsPerDocument`: `s/document`; `exceptionRate`: `ratio`; `availableHours`: `h`; `availableUnits`: `count` | Ручное время до/после, вычислительная мощность, её дефицит. Оставшийся труд = контроль каждого документа + доля исключений × время разбора. Отрицательное высвобождение сохраняется как увеличение труда. Производительность вычислительных потоков не является пропускной способностью всей системы: человеческий bottleneck здесь не измерен. |

Эти адаптеры вычисляют детерминированные агрегаты. Они не порождают прибытия, очереди, план здания или геометрию робота из средних значений. Показатели мощности — оценка модели, а не измеренные результаты внедрения.

## Журнал и имитация

`replaySimulation` воспроизводит реальный журнал. Вход: `resources: [{id,sourceRef}]`, `events: [{id,resourceId,state,startedAtSeconds,endedAtSeconds,completedOperations?}]`, `observationStartSeconds`, `observationEndSeconds`. Все времена — измерения в `s`, счётчик завершений — в `count`. Состояния: `idle`, `moving`, `working`, `charging`, `maintenance`, `error`. Завершения допустимы только в `working`. Одинаковые ID, неизвестные ресурсы, пересечения интервалов ресурса, события вне окна и неположительная длительность запрещены.

Пробелы в журнале остаются `unknown`, а не превращаются в простой. Полная загрузка и throughput рассчитываются только при полном покрытии времени всех ресурсов. Счётчик только зарегистрированных завершений имеет отдельный ключ `recordedCompletedOperations`. Очередь и ожидание не выводятся из журнала состояний без соответствующих исходных данных.

`simulateFlow` выполняет FCFS-модель на одинаковых параллельных ресурсах. Вход: `resources: [{id,sourceRef}]`, `arrivals: [{id,arrivedAtSeconds: Measurement,serviceSeconds: Measurement}]`, оба измерения в `s`; окно наблюдения как выше и `continuousAvailabilityConfirmed: true`. Каждая запись представляет одну реально зарегистрированную операцию и измеренное время её обслуживания. Непрерывная доступность ресурсов — явное пользовательское модельное допущение; модель не добавляет перерывы, поездки, зарядку, отказы и случайные события.

Очередность: время поступления, затем исходный порядок записей. Ресурс: самое раннее освобождение, затем порядок ресурсов. Начало = max(поступление, освобождение ресурса), окончание = начало + измеренное обслуживание. Для наблюдаемого окна рассчитываются завершения, очередь, её средняя длина, throughput и загрузка. Среднее/максимальное ожидание включает расчётное обслуживание всей входной когорты, в том числе за границей окна; это явно отражено в trace. Последнее прогнозное завершение опубликовано отдельно. Будущие прибытия за пределами переданного журнала не экстраполируются.

Оба метода возвращают `timeline`, `resources`, `durationSeconds`, `observationStartSeconds`; FCFS дополнительно возвращает `jobs`. У timeline-элемента есть `basis: observed|computed`, `sourceRefs`, числовые начала/окончания. `snapshotSimulation(result, atSeconds)` строит состояние на абсолютной шкале этих секунд. Изменение скорости анимации не меняет результат. Максимум: 10 000 событий/операций, 1 000 ресурсов; превышение отклоняется, а не обрезается.

## Проверка и реальная доказательная база

`packages/domain/domain.test.ts` проверяет алгебраические инварианты формул, размерности преобразования секунд/часов, нулевые знаменатели, знак эффекта, FCFS-порядок и сохранение длительностей; контрактные проверки — пустые и некорректные payload. Алгебраические векторы не являются сценариями предприятия и не публикуются в каталоге или демонстрации. Единственное минимальное положительное извлечение измерения — площадь здания из [первичного кейса Kärcher Healthcare Logistics](https://www.kaercher.com/nz/target-groups-transport-logistics/healthcare-logistics.html), наблюдение 2026-09-05. Тест специально доказывает, что площадь здания недостаточна для полной модели уборки. Из источника использовано только фактическое число со ссылкой; текст и изображения не копируются.

Полного реального финансового набора и реального событийного журнала внутри этого доменного пакета нет. Поэтому unit/contract-проверки не являются подтверждением положительного клиентского end-to-end сценария. Его должен отдельно пройти корневой workflow после публикации источников и реальных входов через staging.

Локальная проверка 2026-09-05: отдельный строгий TypeScript typecheck пакета и `npx eslint packages/domain --no-error-on-unmatched-pattern` прошли. Прямой runtime smoke через `node --import tsx` прошёл 12 проверок контрактов и алгебры без создания доменного набора. Первый запуск `npx vitest run packages/domain/domain.test.ts` был заблокирован отсутствующим native binding Rolldown; это ошибка запуска тестового окружения, а не результат тестов. Полный Vitest должен быть повторён корневым workflow после восстановления зависимости; до этого весь suite не объявляется прошедшим.
